## 三、改动清单

### A. `OpenOcean-Release` — 分支 `fix/release-safety`

#### A1. `--rebuild` 校验 + 完整传递级联

**位置**：`openocean_release/cli.py:24`、`openocean_release/orchestrator.py:84,296`

**任务依赖图**（读代码得出）：

```
resolve ──┬── checkout.<name>  (×5 源)
          │      ├── linux.native.<family>        ← 按 family 精确
          │      ├── windows.stage-sources ──┬── windows.native.<family>
          │      │                           ├── windows.python
          │      │                           └── windows.matlab
          │      ├── linux.python
          │      └── windows.python / windows.matlab  （直接依赖）
```

**改动**：

1. 定义显式依赖边表 `TASK_DEPENDENTS`，把上图的边写死
2. 新增 `_expand_rebuild(names) -> set[str]`：对给定任务名求**传递闭包**
3. `cli.py` 增加校验：任务名不在已知集合内 → `ConfigurationError` 退出
4. `linux.native.<family>` 的边**按 family 精确** —— `checkout.pe` 只级联到 `linux.native.pe`，
   不波及其他 family（Q11）
5. **与既有自愈逻辑协调**：`orchestrator.py:582-591` 现在检测到客机源不匹配时会
   `self.rebuild.add("windows.stage-sources")` 并重跑。改造后该处应走同一个
   `_expand_rebuild()`，避免两套级联逻辑并存

**验收**：
- `--rebuild windows.pythn`（拼错）→ 报错退出，非零退出码
- `--rebuild checkout.pe` → 重建 `linux.native.pe` + `windows.stage-sources` 及其全部下游，
  但**不**重建 `linux.native.ray_mode`
- `--rebuild` 不指名的任务仍走哈希复用（`state.json` 的输入输出双匹配语义不变）

#### A2. 发布失败断点续传（F1 决策，替代原"回滚 tag"方案）

**位置**：`openocean_release/github.py:50-81`（`create_public_release` 内部）

**现状**：第 73 行建 tag → 第 79 行 `--verify-tag` 建 Release。中间失败 → 留下无 Release 的 tag，
而拒绝逻辑（`github.py:59-64`）会让该 ID **永久不可发布**。

**改动（不做任何删除）**：

1. 建 tag 前先查询 `refs/tags/v{release_id}` 是否已存在
2. 已存在且**指向锁定 commit** → 跳过创建，直接建 Release
3. 已存在但**指向别的 commit** → 报错退出，错误信息含实际 SHA 与期望 SHA，
   并给出人工处置建议（该 tag 指向错误目标，属真实异常，不可自动处理）
4. 不存在 → 正常创建
5. 预检阶段的"拒绝已存在 tag"逻辑（`github.py:59-64`）改为**只在 tag 指向非锁定 commit 时拒绝**，
   使同一 ID 的重试路径畅通

**为何优于回滚**：不删除任何远端引用，无破坏性；重试是幂等的；
失败不会因"回滚本身也失败"而产生二次故障。

**注意**：`--verify-tag` 语义需复核 —— 它要求 tag 在创建 Release 前已存在，
与"跳过创建"兼容，但需实测确认。

**验收**：
- 构造 Release 创建失败（如临时改错 token）→ tag 留存
- 修好 token 后**重跑同 ID** → 跳过 tag 创建，成功建出 Release
- 把 tag 手工指向错误 commit 后重跑 → 报错退出，信息含实际/期望 SHA

#### A3. 上传集与校验和一致（缺口 6）

**位置**：`openocean_release/orchestrator.py:919-920`（`SHA256SUMS` 写入）、`:1230`（`assets +=`）

**现状**（已由 2026.9.21.3 产物实证）：
- `release-lock.yaml` 声明 `configSha256: c29f5297…`，与实际 `release-config.yaml` 哈希**一致**
- 但 `release-config.yaml` **既不在 `SHA256SUMS` 里、也不在上传集里** → 外部**无法验证**该声明
- `release-notes.md` **在校验和里却不上传**（它是 Release body，见 `:917`）

**改动**：
1. `release-config.yaml` 加入 `assets` 上传集与 `checked_paths`
2. `release-notes.md` 从 `checked_paths` / `SHA256SUMS` 中**移除** —— 它不作为资产发布，
   不应被校验（二选一，选了"不上传"这一侧，因其本就是 Release body）
3. 检查同一段的 `set(checksum_entries) != expected_checksum_names` 断言（`:1225-1227`）随之同步，
   否则会误报 "SHA256SUMS file set differs"

**验收**：
- 新发布的 `SHA256SUMS` 含 `release-config.yaml`、不含 `release-notes.md`
- 用公开 Release 的资产能独立验出 `release-lock.yaml` 里的 `configSha256`
- 未改动的发布（如已有 2026.9.21.3）行为不受影响

#### A5. 更新 `docs/runner-environment.md`

补记两条本次审计发现但文档未载的事实：

1. **VM 不在系统 libvirt 域中** —— 跑在 `ci_server` 的用户态会话（`/run/user/1008`）。
   因此以其他用户身份运行流水线会**看不到 VM**；流水线能跑通仅因 runner 以 `ci_server` 运行。
   这是承重耦合，必须记录
2. **镜像稳定性原则** —— 镜像以 digest 锁定，是编译环境，不随项目变动

#### A6. 产物权限统一（F5）

**现状**（实测）：`assets/` 下 Windows 产物为 `-rw-------`（600），Linux 产物为 `-rw-rw-r--`（664）。
成因是两条不同的写入路径 —— Windows 包经 `scp` 从客机拷回，Linux 包本地生成。

**改动**：写入 `assets/` 后统一 `chmod 640`（owner 读写、组只读），
在 `_seal` 阶段或各产物落盘后统一施加。

**验收**：新发布的 `assets/` 下**全部** 11 个资产权限一致为 640。

2. **`openocean/field-release:2026.09` 从未被构建过** —— `docker images` 中不存在，

   A4 的删除依据因此更强。
3. **`openocean/ci-dist:emsdk6.0.8-node22.22.1-eigen3-v1`**（`c5097573d6b8`）是带 eigen3 的镜像，
   属 WASM/网站那条线，**与 Field 发布路径无关**。它的存在不构成"发布镜像缺 eigen3"。
4. **Windows 原生包为 4 段式**（实测 PE，147 条目，反斜杠路径）：
   `archives/`（shared+static 两个子 zip）+ `shared/bin/`（DLL 与 standalone exe）+
   `shared/include/` + **`metadata/`**（`DEPENDENCIES.md`、`LICENSE-DECLARATION.txt`、
   `licenses/LICENSE`、`licenses/third-party/{eigen,nlohmann}/`）。
   契约的 `standalone_executables: true` 在此为实物（`OpenOcean-Field-PE-{RAM,RAMGeo,RAMS}.exe`）。
   **注**：此前基于 Linux 包推断的"3 段式"不准确 —— Linux 包无独立 `metadata/` 顶层目录。
5. **MATLAB toolbox 为标准 OOXML 包**：`[Content_Types].xml`、`_rels/.rels`、
   `_xmlsignatures/`、`fsroot/+openocean/+{builders,config}/`。
   8 个后端各有 Builder 类，与 Python SDK 的 8 个 backend 对应。
6. **Windows Python bundle** 同为 26 条目结构，21 个 wheel（`win_amd64` 平台标签）。
